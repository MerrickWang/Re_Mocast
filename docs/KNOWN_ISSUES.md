# 已知问题与复现边界

更新：2026-09-27。本文区分已观察到的结果、代码可确认的问题与尚未验证的解释。
当前仓库是非官方机制复现，不能标记为完成论文数值复现。历史工程验收记录不改变这一结论。

## K01 与论文数值仍有明显差距

当前 Shanghai 测试 CSI 为修复前 0.202794、修复后 BS=2 0.206922、BS=6 0.206699。
修复前后使用单一运行种子；没有多种子方差、配对置信区间或完整的服务器环境归档。
BF16 网格/损失修复与 batch 调整均未消除性能差距，但这些实验不能确定差距的唯一原因。

论文对齐需要核实数据版本、预处理、划分、网络设置和指标聚合口径。
不要仅从调参后的测试分数推断作者方法是否有效，也不要把工程单测视为精度复现证据。

## K02 H5 编码与事件划分未核实

- 文件为 train/test 分组，序列通常是 uint8 [25,501,501]；根/组属性未提供单位与时间戳。
- 当前假设 `dBZ = pixel × 70 / 255`。原值超出 70 使直接解释为 dBZ 不太合理，但不能由此证明缩放公式。
- `sanitize.clip=[0,70]` 的实现会将越界值替换为 fill=0，并非上界截断；错误编码会产生大量清零。
- train 组以固定 seed=2026 划出验证集，1381/153；526 个 test 序列沿用原分组。
- 样本编号互斥不代表天气事件独立。默认每 split 抽 32 个序列，精确重复为 0 不证明无时间重叠。
- 名义间隔为 6 分钟，当前未裁剪而将整幅 501×501 缩至 128×128；均需与数据制作方核对。

下一步应获得 H5 生成脚本、编码/缺测说明、事件和时间索引，以及论文的 split 清单。
详见 [作者确认清单](作者确认清单.md) 与 [H5 审查](Shanghai诊断与实现审查.md)。

## K03 强回波低估与长时平滑

修复前测试集在 40 dBZ 的召回率约 0.053，预测覆盖率 0.0342%，真实覆盖率 0.1719%；35 dBZ 也存在低估。
修复后两个 batch 设置的逐阈值召回率尚未归档，不能直接把旧数值当作新模型结果。

旧权重验证集完整模型 CSI 0.231472，高于持久性 0.172272，且 20 个预测步都高于基线。
只保留运动或只保留源汇的 CSI 分别为 0.181942 / 0.153267，支持两分支共同发挥作用。
这些是固定权重的事后探测，不是独立训练消融，不能据此断定哪个模块存在因果缺陷。

算子探测中，单像素脉冲重复移动 0.5 像素 20 次，峰值约 0.1762；单次移动 10 像素峰值约 1。
这证明重复双线性插值可平滑峰值，**没有证明它是实测差距的主因**。
实际运动场是可变的，不能把常量流的单次重采样直接替换论文递推公式。

旧模型验证集强度乘数 1.1 将 CSI 从约 0.2315 提到 0.2587；该数值不是测试结果，也不适用于所有检查点。
仓库尚无正式的校准工具。后续应在验证集检查逐阈值 precision/recall、逐时效曲线与源汇幅值，再决定实验。

## K04 结构与优化器设置包含假设

PMM patch/stride、注意力缩放、潜空间运动尺度、小波 LL 处理、MSM 核和调制网络、时序网络宽度/深度、weight decay、早停 patience 等尚未与作者实现逐项核对。
当前配置将其显式参数化。**参数化不保证拿到作者信息后仅改 YAML 就能完全对齐**，结构差异可能需要修改代码。

作者官方代码/权重尚未在本项目中取得并完成对照，不作“官方代码一定未公开”的时效性断言。
MoCast+、SEVIR 和 MeteoNet 保留实现入口，但此轮未提供对应真实数据上的完整数值验证。

## K05 评估批次权重与精度口径

代码位置：`mocast/metrics/evaluator.py`、`mocast/engine/trainer.py`、`mocast/tools/eval.py`。

`Evaluator.update()` 对每个 batch 的 MSE/MAE/SSIM/LPIPS 均以 `n=1` 累加，最后一个较小 batch 被赋予与完整 batch 相同的权重。
例如测试集 526 个样本，BS=2 恰好整除；BS=6 有 87 个完整 batch 和 1 个四样本 batch。因此这些指标的精确跨 batch 比较有轻微汇总偏差，实际大小需重算确认。
CSI/HSS 与池化 CSI 使用全局混淆计数，不受此处的等权均值问题影响。

训练内验证使用配置的 AMP，独立 `eval` 和 `diagnose_forecast` 默认 FP32；诊断工具支持 `--amp`。
同一权重的 `best_score` 与独立诊断可能略有不同。正式比较应记录并统一推理精度与评估 batch。

发布准备阶段只记录问题，未修改历史评分实现或重算服务器结果。
后续修复应按样本/帧或像素数加权，并用不等长末批次验证 batch 不变性，再同时重评所有检查点。

## K06 断点恢复状态不完整

代码位置：`mocast/engine/trainer.py` 的 `save_checkpoint()` / `load()`。

当前保存模型、优化器、epoch、score、config 和 monitor。
没有完整保存/恢复 scheduler、GradScaler、Python/NumPy/PyTorch/CUDA 随机状态、历史最佳 epoch/score 和早停等待次数；`last.pt` 的 score 也不一定是历史最佳分数。
恢复后可能改变学习率轨迹、早停和最佳检查点选择，`epochs_run` 仅反映本次进程记录的历史。

加载旧权重用于推理是支持的；续训不能视作与不间断训练完全等价。
修复前后对照应从头开始，使用独立目录。后续需增加“连续训练与中断恢复轨迹一致”的测试。

## K07 评估工具会保存配置，LPIPS 有下载和回退行为

`eval` 和 `visualize` 调用 `prepare_run()`，会在输出目录保存配置；建议独立指定 `--output`。
诊断工具不调用该方法，不改写训练配置。

首次启用 LPIPS 可能下载 AlexNet 权重，网络缓慢时看起来像验证卡住。
`lpips` 初始化失败后可能回退到 VGG 特征距离，后者不是等价 LPIPS。
报告必须检查 `lpips_backend`；关闭指标或初始化失败导致的 NaN 不应记成 0 分。
